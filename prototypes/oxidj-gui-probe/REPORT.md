# ADR-001 isolated egui probe — evidence report

Status: **CURRENT PROTOTYPE GATES INCOMPLETE / NOT QUALIFYING**. Owner decision (2026-10-24) defers the 500k-row 60fps qualification to a later final-framework stage. Treating that target as achievable for current planning is not a measured pass; the target remains unverified. This probe is isolated; no GUI dependency was added to the root workspace or production manifests. No personal media was opened.

Latest interaction implementation: the uncommitted fix following `c4c79a4` captures the source row on pointer press, marks the drag active when egui reports `dragged()`, and resolves a primary-button release against laid-out row rectangles after row layout. All 11 probe tests and `cargo xtask ci` passed after this code edit. Post-fix live verification could not launch the probe because Bot Screen `:20` was inaccessible (see below); no current-build live interaction or accessibility pass is claimed. Earlier live checks on 2026-10-25 established AT-SPI app discovery and named controls in the nested session. The private Hermes Bot Screen then showed an older build of the 200k probe rendered and confirmed click selection through probe output; drag/reorder was attempted but not observed to succeed. Earlier commit `058e205` records observer-free auto-scroll at both 200k and 500k rows, with visible progression in a 30fps portal recording. An earlier nested Hyprland run returned presentation feedback for stationary rendering at both sizes (about 30fps), but feedback-enabled sustained scrolling remains unmeasured. The 30fps portal capture cannot establish app frame rate. Real screen-reader and supported-platform checks also remain outstanding. No framework gate or production admission is passed by this evidence.

In the separate nested Wayland session, 200k reported 341 update callbacks / 16,072ms = 21.2 callback/s after one End key; 500k reported 454 / 15,010ms = 30.2 callback/s after one End key. Both reached the last row with matching widget focus and nonzero scroll offsets. At 500k, Shift+Up twice produced `Focused row: 499995 | selected: 4`; plain Up produced row 499994 with one selected row. Two Ctrl+Space attempts left the visible selection count at 1; keyboard toggle was not demonstrated. A screenshot showed the 500k focused row and range visibly highlighted; both probe windows were reported open at the end of that earlier session. These are historical observations, not a claim about current window state. These are callback counts around sparse navigation events, not sustained-scroll workload or presented-frame measurements. The earlier probe was not reopened after its auto-close; the user later authorized this separate nested Wayland session. Host workspace and display mode were untouched. The host Hyprland mode remains 3840×2160@30Hz; 1920×1080@60Hz and 2560×1440@59.95Hz are available but were not activated. 60fps performance remains unmeasured.

## Sustained-scroll frame-observation attempt (2026-10-24)

No actual-frame measurement was obtained in these historical attempts; callback rates above are not substitutes. The first eframe-bound `wp_presentation_feedback` attempt used synchronous registry setup and roundtrips; it advanced only three update callbacks in about 20 seconds and emitted no feedback. The async observer then removed roundtrips and shared-display reads, but this did not prove feedback would arrive. Two older probe windows remained mapped in the nested session; neither used the revised build. A bounded live run of the revised 200k probe then timed out after 105 seconds with only three update callbacks and no report or feedback. This showed no usable evidence and was stopped.

As a distinct path, the standalone probe was built with `--features eframe/wgpu`, then run with `WGPU_BACKEND=vulkan` and `OXIDJ_PRESENT_SCROLL=1` at 200k rows. The run emitted `probe_finished rows=200000 update_callbacks=21 elapsed_ms=15095 callback_fps=1.4 keyboard_events=0 focused_row=110 widget_focused_row=Some(110) scroll_offset=2970.0 ... presentation_feedback_presented=0 presentation_feedback_unique_timestamps=0 presentation_fps=0.00 presentation_feedback_discarded=0 last_refresh_ns=None presentation_error=None`. The command ended at its 22-second timeout (exit 124); the report arrived at 15,095ms. This is callback and scroll-state evidence only, not frame-rate evidence. The requested Vulkan/WGPU path produced no presentation events or protocol error, so no 500k repeat was run. Actual sustained-scroll presented-frame rates remain NOT MEASURED at both sizes.

Earlier nested capture attempts (`WAYLAND_DISPLAY=wayland-2`) timed out with `grim` (exit 124), and host `computer_use` capture failed with X11 `GetImage` error 8. Do not re-label callback counts as frame rates. A follow-up bounded protocol trace used `WAYLAND_DEBUG=client` for the same 200k WGPU/Vulkan run (22-second timeout, exit 124). The trace contained 21 client `wp_presentation.feedback(wl_surface#27, ...)` requests and zero incoming `wp_presentation_feedback.presented` or `.discarded` events; the probe's own 15,106ms report likewise recorded zero presented/unique timestamps, `presentation_fps=0.00`, no protocol error, and only 21 update callbacks. The trace therefore narrows the failure: requests are sent on the live surface, but this run receives no presentation-feedback event. It still provides no actual presented-frame rate and no sustained-scroll result; 500k was not retried. Needed capability is a compositor/native observer that can return actual presentation timestamps (or a verified alternate supported measurement source), not merely another request-side trace. Presentation feedback remains unusable on this nested eframe surface; ADR-001 stays NOT PASSED and M3 remains gated.

### Observer-free auto-scroll portal capture (2026-10-24)

To avoid the observer path that stalled eframe, `OXIDJ_PRESENT_SCROLL=1` enabled deterministic 100ms focus/scroll steps and disabled `PresentationObserver`. Fresh 200k and 500k WGPU/Vulkan runs each reported about 30 update callbacks/s, then reached focused row 119 with scroll offset 3213 after 15s. A portal recording captured the nested desktop at 3812×2100, constant 30fps. At 10s, sampled frames visibly showed auto-scroll progression (focused row 50 at 200k; row 42 at 500k). For each recording, FFmpeg `mpdecimate,showinfo` counted changed frames in a 1400×850 crop of the probe list: 200k had 136 changed frames across 11.967s (11.36 changes/s); 500k had 137 across 13.7s (9.93 changes/s). These are portal-sampled visible-content changes, not compositor presentation timestamps or app frame rates. The 30fps capture cannot establish performance at 60fps; sustained-scroll presented-frame performance remains unmeasured. The owner later deferred the 60fps qualification to a later final-framework stage; no pass is claimed. Current prototype-stage accessibility and interaction gates remain incomplete.
