# OneLibrary and rekordbox interoperability research

Research snapshot: 2026-10-15. This is an evidence boundary, not a claim that OxiDJ can already write a player-compatible library. Primary evidence and independent format analysis are linked below; detailed captures and provenance are in `/home/senci/dev/oxidj/.wiki` (not checked into this repository).

## Interchange strategy

1. Treat Rekordbox XML as the first documented, user-mediated interchange boundary for playlists and the fields explicitly listed in its format PDF. Build a conservative parser/exporter only against fixtures, with unsupported fields reported rather than silently dropped.
2. Treat legacy PDB/ANLZ as a separate reverse-engineered adapter, not as OneLibrary. Any implementation must pin its upstream references/version and preserve unknown sections.
3. Treat OneLibrary as a compatibility target requiring partnership/public specification or empirical validation. Do not write undocumented databases or claim broad hardware compatibility from the OneLibrary name alone.
4. Internal identity must be independent of vendor IDs and file paths. Retain source IDs/URIs, playlist ordering/tree, original field values, and provenance; path relocation and duplicate audio require explicit reconciliation, not silent reassignment.
5. Import/export must be non-destructive and report unsupported/lost fields before writing. Keep original media and export directory untouched until the user approves a staged result.

## Fixture and experiment plan

Create disposable USB media and preserve read-only copies/hashes before and after each experiment. Record app build/version, OS, exact device model/firmware, filesystem, locale, and action sequence. Use clean fixtures generated by official software; do not use personal libraries as test inputs.

A. XML baseline: in a current Rekordbox build, import minimal XML containing (1) one track and nested playlists, (2) duplicate names at different and same tree levels, (3) escaped/non-ASCII names, (4) absolute `file://localhost` locations with spaces/non-ASCII, (5) TrackID and Location playlist keys. Compare the imported view and any Rekordbox re-export; document normalization and rejection behavior.

B. Metadata round-trip: generate separate XML tracks with multiple tempo changes/meter/beat-in-bar, tonalities, colored tracks, ratings, multiple cue types, memory cue, loop start/end and missing optional elements. Compare values and precision after import/export. Label each field exact, normalized, dropped, or unverified; never infer from display alone.

C. Legacy USB differential: export the same small controlled library through Rekordbox Device Library. Capture `/PIONEER/rekordbox/export.pdb`, referenced ANLZ files, and filesystem tree before/after changing exactly one field at a time. Parse using pinned Deep Symmetry/Crate Digger references; verify mapping, unknown bytes, endianness and stale-file behavior. Do not modify the only copy.

D. OneLibrary black-box boundary: using official Rekordbox conversion/export on a spare drive, capture directory inventory and file hashes for empty, one-track, playlist/cue/grid/key/waveform variants. Diff one controlled change per export and inspect whether generated artifacts are parseable SQLite or opaque/encrypted; do not assume schema based on filenames or third-party claims. Use Rekordbox UI to confirm browsable tracks/playlists, then test only available listed devices/firmwares. Verify backup/restore and conversion-overwrite warning behavior.

E. Vendor passthrough: introduce a field/value produced by each supported vendor, then import and re-export without editing it. Test byte/semantic retention independently for unknown metadata and unknown container sections. If no representable safe passthrough exists, preserve the complete source artifact and explicitly mark unsupported.
